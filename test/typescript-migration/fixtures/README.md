# Runtime compatibility fixtures (P0)

Run from the repository root with `node --test test/typescript-migration/runtime.test.cjs` after installing workspace dependencies. These fixtures are deliberately CommonJS: they freeze the existing runtime before the TypeScript declaration migration. The test imports actual workspace modules, restores `global.think` and its module cache after each test, and never starts a server or connects to a database.

## Contracts and limitations discovered

- `think.service` in a single-module app treats the second argument as a constructor argument. Calling it with only a name supplies one `undefined` argument. In a multi-module app the second argument selects the module, defaulting to `common`; unrecognized modules do not fall back. Object exports retain identity; constructors produce instances. The CommonLoader unwraps `__esModule.default`, retains slash-separated nested names, and sets constructor prototype `__filename`.
- Common services are merged into module registries before module overrides. **Context.service only forwards arguments**, but **Controller.service infers its context module** when the service is available there and the second argument is not a registered module name (`packages/thinkjs/lib/extend/controller.js`, service method). Thus with an admin override, `ctx.service('shared')` selects common while `controller.service('shared')` selects admin. An arbitrary second string becomes a controller constructor argument in this case, whereas Context interprets it as a module name and throws. A declaration migration must not silently unify these APIs.
- Model lookups fall back to the base Model, use the basename of nested names as `modelName`, and retain the selected model registry identity. Context defaults registry selection to its request module. An explicit Context model-module override changes the registry **without changing the request module used for model/cache config**. Global `think.model` uses its explicit module for both. The adapter fixture is inert; these tests cover construction, not database behavior.
- Config lookup is `(name, undefined, module)`; a second string is a value to set, not a module selector. Single-module setters return the Config instance; multi-module setters return `undefined`. Multi-module sets support `true` (all) and comma-separated names (unknown entries ignored); unknown read modules fall back to common. `undefined` means read, so it cannot be assigned through this wrapper. Dotted keys and explicit `null` work.
- Config loading merges common base, module base, common environment, module environment, in that order. Objects merge deeply. Arrays merge by index and **retain base trailing entries** when the overriding array is shorter. This is not an array-replacement contract.
- Extend order is system, configured entries in array order, then application extensions. Multi-module apps only read `common/config/extend.js` and `common/extend/*`; module-specific extension files are ignored. Methods keep their receiver; getter/setter descriptors survive application. A value assignment cannot replace an existing getter-only property with this helper (the `isGet` fixture freezes that edge case). Getter/setter redefinitions are supported.
- Extension configuration entries that are functions are rejected by the existing loader with a console error, not called as factories. `loadConfigByName` directly requires config exports rather than unwrapping `__esModule.default`; the service default-export interop must not be assumed to apply to configuration files. These two source-observed limitations are documented here, not exercised as supported fixture APIs.
