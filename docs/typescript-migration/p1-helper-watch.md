# P1 helper watch prototype

This slice of [#1795](https://github.com/thinkjs/thinkjs/issues/1795) stacks on
[#1804](https://github.com/thinkjs/thinkjs/pull/1804). It adds a reusable live
**declaration** workflow, not a full application dev/build coordinator. The installed-tarball acceptance gate also exercises live Service
add/rename/delete through the packed API, then reruns semantic checking. Existing
framework runtimes, templates and published versions are unchanged.

## Scope

`think-ts-helper watch` and the `watch(options)` JS API reuse the existing
Service/Model/Config/Controller generation and output ownership rules. They add:

- First-success `ready` event/Promise, initial failure rejection and CLI exit 1.
- Serialized full-scan polling with configurable interval, no unchanged writes
  or update events, and naturally coalesced edits between polls.
- Recovery after later source/ownership/parser failures, deduplicated diagnostics
  and a recovery update even when the restored declarations have identical bytes.
- Source addition, deletion, nested directory rename and module-layout changes,
  including enabled Config and Controller member changes.
- Idempotent close, early-close readiness rejection, process-local duplicate
  output reservation and CLI SIGINT/SIGTERM cleanup.
- Preservation of unrelated files and existing opt-out cleanup of helper-owned
  declarations when a new watch session starts with different flags.

See the [helper README](../../packages/think-ts-helper/README.md#watching-declaration-inputs)
for exact API/event/exit semantics and sample integration. The initial failure
rule deliberately refuses readiness based on previously generated declarations.
After readiness a caller must consume diagnostics and run its own compiler;
recovering helper output does not prove semantic correctness.

## Why polling first

The generator is synchronous and presently inspects whole source sets, enabled
static config and installed framework inputs. Scheduling one poll only after
completion avoids overlapping runs and a backlog without introducing a new
watcher dependency or a partially invalidated cache. It also finds directory
removal, timestamp-preserving edits and installed system-input changes.

This is not incremental analysis. Every poll re-reads/parses applicable inputs
and compares generated bytes, even when idle. It blocks the caller's event loop,
so the CLI is preferable to embedding it in a busy server. There is no OS file
watcher limit dependency, but large-project CPU/performance acceptance remains
open. Watch options are fixed per session; no helper config/tsconfig is parsed.

Reproduce the baseline:

```sh
node packages/think-ts-helper/scripts/benchmark.js 1000
node packages/think-ts-helper/scripts/benchmark-watch.js 1000
```

One Linux / Node 24.22.1 run with 1,000 simple TS services measured 66 ms initial
generation and 30 ms median unchanged generation. Watch readiness took 85 ms;
add/rename/delete notification took 570/536/529 ms with the default 500 ms poll.
These observations include parsing, output comparison and poll delay where
applicable, but exclude compiler and app startup. They are not a portable SLA
or agreed performance budget; no flaky timing assertion is added to CI.

## Artifact boundary and remaining work

The helper owns declarations, not runtime build output. Its tests explicitly
preserve an existing compiled JS file after deleting the corresponding source.
This is intentional: blindly mirroring/deleting arbitrary app directories would
not provide a safe ownership contract. The preceding installed-application gate
still owns and cleans its fixture's entire build directory before compilation.

A subsequent development coordinator needs a compiler-emitted artifact manifest
or an equally explicit build ownership contract for JS, source maps and copied
resources; deleted source must remove its owned outputs and trigger the runtime
reload path. It must order initial generation, semantic checking, compilation
and application readiness, and propagate errors/exit for all processes. Current
`think-watcher`/`think-typescript` behavior is unchanged by this PR.

Other limits remain: cross-process writer locking, multi-file transactional
output, cached incremental generation, config-file reconfiguration, Windows/macOS
validation, application restarts, templates and the broader P1/P2 gates. No P1
completion, package publication or merge is claimed.

## Validation

On Linux / Node 24.22.1 / pnpm 11.6.0:

- Root lint and test passed, including the helper watch suite and unchanged
  TypeScript migration/compiler/runtime tests.
- The focused watch suite passed 15 tests. One real case-insensitive-filesystem
  test is skipped on this case-sensitive Linux volume; a controlled mixed-policy
  filesystem regression runs here and passes.
- Installed-tarball application gates passed with TypeScript 3.9.10 and 5.9.3,
  including the new watch check, semantic compilation, real clustered HTTP
  requests and separate runtime-only installations.
- Independent review identified a case-alias reservation issue; physical
  directory identity checks and a stable lexical reservation fixed it, with
  a regression covering output creation across mixed mount case policies.
- Inventory, syntax and whitespace checks passed.

Local workspace checks reused existing dependencies and the existing CLI
fixture template cache under a writable test HOME; pnpm's automatic pre-run
install was disabled. An initial test attempt with the default read-only HOME
failed in the existing CLI fixture before that environment setup was corrected.
Installed application gates used fresh consumers and existing offline package
caches, not workspace node_modules or cold registry downloads. Windows/macOS,
Node 20/22/26 and actual case-insensitive volumes were not tested locally. Root
Memcached/MongoDB exclusions and legacy TODOs remain unchanged. Remote CI is
reported separately for the exact PR head.
